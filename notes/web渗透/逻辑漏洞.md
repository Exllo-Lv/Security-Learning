# 逻辑漏洞深度攻防笔记

## 概述

逻辑漏洞的本质是业务实现层面的设计缺陷——程序在业务流程上的逻辑校验不严谨，导致攻击者可利用合法的功能路径达成非预期的恶意目的。此类漏洞流经的是合法业务流量，传统 WAF/IDS 等防护设备难以通过特征匹配进行拦截，因此挖掘与防御均依赖对业务模型的深度理解。

> **面试高频考点：** 逻辑漏洞与 OWASP Top 10 注入类漏洞的本质区别在于——前者无需向应用注入恶意 Payload，而是利用正常功能路径中的校验缺失或时序竞争，属于"合法流量、非法逻辑"的范畴。

## 第1章：认证与会话管理缺陷

### 1.1 验证码机制缺陷

#### 1.1.1 验证码爆破（Brute-Force on OTP）

**漏洞根因：** 服务端对短信/邮箱验证码缺乏错误尝试次数限制，且验证码有效期过长（如 15 分钟），验证码熵值过低（如 4 位纯数字），攻击者可遍历全部可能性实现爆破。

**漏洞存在前提：**
1. 验证码未设置短期失效机制
2. 服务端无连续错误尝试阈值锁死策略

**测试入口 → 篡改点 → 预期危害：**

```
① 测试入口：短信登录/密码找回 → 输入目标手机号 → 发送验证码
② 篡改点：  提交验证码的 POST 请求 → 将验证码字段发送至 Burp Intruder（Payload: 0000-9999）
③ 预期危害： 绕过身份验证登录任意用户账号 / 重置任意用户密码
```

**实战案例：**

```
http://t.pp.cc/member.php?mod=login&action=register&app=time&type=sina
https://xinminghui.com/member/find-pwd
```

**修复建议：**

```php
// 服务端关键校验逻辑
$max_attempts = 5;  // 单验证码最多尝试 5 次
$expire_seconds = 300;  // 验证码有效期 5 分钟

$cache_key = "sms_code:" . $phone;
$attempt_key = "sms_attempt:" . $phone;

$attempts = redis()->get($attempt_key) ?: 0;
if ($attempts >= $max_attempts) {
    redis()->del($cache_key);  // 验证码即时失效
    throw new Exception("验证码尝试次数过多，请重新获取");
}

if (redis()->get($cache_key) != $input_code) {
    redis()->incr($attempt_key);
    throw new Exception("验证码错误");
}

// 验证成功后立即清除
redis()->del($cache_key);
redis()->del($attempt_key);
```

#### 1.1.2 敏感凭证响应体回显（Credential Leakage in Response）

**漏洞根因：** 验证码本应在服务端生成后仅通过短信/邮件等带外通道下发至用户，但后端将验证码明文写入 HTTP 响应体返回至前端，攻击者可直接从响应包截获。

**测试入口 → 篡改点 → 预期危害：**

```
① 测试入口：注册/找回密码 → 触发发送短信验证码
② 篡改点：  拦截发送验证码的 HTTP 响应 → 检查 Response Body 是否含 code/smsCode/verifyCode 字段
③ 预期危害： 获取任意手机号的验证码，实现任意用户注册/密码重置
```

**实战案例：**

```
http://www.founderfx.cn/     (密码找回处)
http://www.farenhui.com/Register.asp
https://www.huibaike.com/
```

**修复建议：** 验证码在服务端生成后仅通过带外渠道（短信网关/邮件服务）下发，**严禁**写入 HTTP 响应体。响应体仅返回成功/失败状态码。

---

#### 1.1.3 验证码未绑定用户会话（Unbound OTP）

**漏洞根因：** 服务端在验证码校验阶段，仅比对验证码值本身是否匹配，**未校验验证码所属的用户身份与会话中的用户身份是否一致**。攻击者使用自己手机接收验证码后，将请求中的用户标识（UID/手机号）替换为目标受害者，即可利用自己的验证码通过目标用户的校验。

> **面试高频考点：** 该漏洞的核心在于"凭证（验证码）与主体（用户）的解耦"——服务端将验证码存入了全局 Key-Value 存储，但 Value 中缺失了用户身份维度。

**测试入口 → 篡改点 → 预期危害：**

```
① 测试入口：短信登录/密码重置 → 使用攻击者手机号 138xxxx 接收验证码
② 篡改点：  提交验证码的请求 → 将 phone/uid 参数从 138xxxx 替换为受害者 139xxxx
③ 预期危害： 攻击者凭借自己的验证码登录/重置受害者账户
```

**实战案例（登录时）：**

```
http://m.miao-duoduo.com/panel/index.php?go=user&do=logout
```

**修复建议：**

```java
// 会话维度绑定校验
String sessionUid = session.getAttribute("sms_uid");
String requestUid = request.getParameter("uid");
String sessionCode = session.getAttribute("sms_code");

if (!sessionUid.equals(requestUid)) {
    throw new AuthException("验证码与用户身份不匹配");
}
if (!sessionCode.equals(requestCode)) {
    throw new AuthException("验证码错误");
}
// 校验通过后立即清除 Session 中的凭证
session.removeAttribute("sms_code");
session.removeAttribute("sms_uid");
```

```
- 验证码暴力破解测试（无尝试次数限制 → Burp Intruder）
- 验证码重复使用测试（同一验证码多次提交是否有效）
- 验证码客户端回显测试（响应体是否包含明文验证码）

- 验证码自动识别测试（图形验证码是否具备足够干扰度）
```

### 1.2 Session 与 Cookie 安全缺陷

#### 1.2.1 Session 固定攻击（Session Fixation）

**漏洞根因：** 服务端在用户认证前后未重新生成 Session ID，攻击者可预先获取一个有效的 Session ID（如通过 URL 参数注入 `?PHPSESSID=attacker_known_value`），诱导受害者使用此固定 Session ID 完成登录。由于登录后 Session ID 不变，攻击者使用同一 Session ID 即可接管受害者的已认证会话。

```
参考文章：https://juejin.cn/post/6844904130268364808
```

**修复建议：**

```java
// 登录成功后强制重新生成 Session ID
HttpSession oldSession = request.getSession(false);
if (oldSession != null) {
    oldSession.invalidate();
}
HttpSession newSession = request.getSession(true);
// 迁移必要数据至新 Session
newSession.setAttribute("user", authenticatedUser);
```

---

#### 1.2.2 Session 劫持（Session Hijacking via File Exposure）

**漏洞根因：** PHP 等语言默认将 Session 数据以文件形式存储在服务器磁盘（路径如 `/tmp/sess_<PHPSESSID>`），若应用存在路径遍历、任意文件读取或目录浏览漏洞，攻击者可读取到其他用户的 Session 文件，进而窃取 Session ID 实现会话劫持。

**Pikachu 靶场代码分析——Session 文件存储：**

```php
@$path_parts = pathinfo(__FILE__);
$save_session = $path_parts['dirname'] . '\Session_save';
@session_save_path($save_session);  // Session 存储在 Web 可访问目录
@session_start();
```

> **关键缺陷：** `session_save_path()` 设置在了 Web 目录下，攻击者通过目录扫描获取 Session 文件名后，构造 `PHPSESSID=受害者的SessionID` 即可直接接管对方会话。

**修复建议：**
1. Session 存储目录应设置在 Web 根目录之外
2. 启用 `session.cookie_httponly = 1` 和 `session.cookie_secure = 1`
3. 优先使用 Redis/数据库统一管理 Session，关闭文件存储模式

---

#### 1.2.3 Cookie 仿冒攻击（Cookie Spoofing）

**漏洞根因：** 服务端将用户身份标识（如 UID、角色级别）明文或可逆编码存储在 Cookie 中，且服务端未对 Cookie 做完整性校验（如 HMAC 签名）。攻击者修改 Cookie 中的身份字段即可冒充其他用户。

**测试入口 → 篡改点 → 预期危害：**

```
① 测试入口：登录账户 A → 访问任意需认证的页面 → 截获 Cookie
② 篡改点：  登录账户 B → 将请求中的 Cookie 替换为账户 A 的 Cookie
③ 预期危害： 账户 B 以账户 A 的身份操作全站功能
```

**修复建议：**

```python
# Flask 示例：使用 itsdangerous 对 Cookie 进行签名
from itsdangerous import TimestampJSONWebSignatureSerializer as Serializer

s = Serializer(app.config['SECRET_KEY'], expires_in=3600)
cookie_value = s.dumps({'uid': user.id})
response.set_cookie('session', cookie_value, httponly=True, secure=True)
```

---

#### 测试关注点（Session/Cookie 模块）

```
- 登录前后 Session ID 是否变��（防固定）
- Cookie 中是否包��可推测的用户标识（UID/Role）
- Cookie 是否设置 HttpOnly / Secure / SameSite 属性
- Session 存储路径是否在 Web 可访问范围内
```

### 1.3 并发条件竞争导致的认证绕过

**漏洞根因：** 在高并发场景下，多个线程同时进入"凭证有效性校验 → 业务操作"的临界区，由于校验与操作之间存在时间窗口且未加锁，导致同一凭证被多次使用或身份绑定被覆盖。

> **面试高频考点：** 并发漏洞的本质是 TOCTOU（Time-of-Check to Time-of-Use）问题——校验时的状态与使用时的状态不一致。

**典型案例——Bilibili 直播抽奖并发：**

```
测试入口：点击"十连抽"按���
篡改点：  拦截抽奖请求，使用 Burp Intruder 以 20+ 线程并发发送
预期危害：单次消耗的抽奖券被判定为多次有效，实现超额抽奖
```

**修复建议：**

```java
// 接口幂等性设计：使用 Redis 分布式锁
String lockKey = "draw_lock:" + userId;
boolean locked = redis.setnx(lockKey, "1", 5);  // 5 秒超时
if (!locked) {
    throw new BizException("操作过于频繁，请稍后重试");
}
try {
    // 原子性扣除抽奖券
    int updated = db.update("UPDATE user SET tickets = tickets - 10 WHERE id = ? AND tickets >= 10", userId);
    if (updated == 0) throw new BizException("抽奖券不足");
    // 执行抽奖逻辑...
} finally {
    redis.del(lockKey);
}
```

## 第2章：访问控制缺陷（越权）

> **本质定义：** 越权漏洞的根因是服务端对数据归属或操作权限缺乏校验——要么未校验请求者是否为数据的合法所有者（水平越权），要么未校验请求者是否具备该操作的权限级别（垂直越权）。

### 2.1 水平越权（Horizontal Privilege Escalation）

**定义：** 相同权限级别的用户 A 通过修改请求中的资源标识符（如 UID、OrderID），访问或操作同级别用户 B 的数据。

**Pikachu 靶场代码分析：**

```php
// 漏洞代码 —— op1_mem.php
$username = $_GET['username'];  // 直接取用户传入的参数
$sql = "SELECT * FROM member WHERE username = '$username'";
// 未校验 $username 是否属于当前登录用户
$result = mysqli_query($conn, $sql);
```

> **关键缺陷：** `$_GET['username']` 由客户端传入，直接拼入 SQL 查询且未与 Session 中的当前用户身份进行比对。攻击者将 `?username=kobe` 改为 `?username=admin` 即可查看 admin 的个人信息。

**修复建议：**

```java
// Spring Security + 注解式权限校验
@PreAuthorize("@dataPermissionChecker.canAccess(#id)")
@GetMapping("/order/{id}")
public Order getOrder(@PathVariable Long id) {
    return orderService.findById(id);
}

// DataPermissionChecker 实现
public boolean canAccess(Long orderId) {
    Long currentUserId = SecurityContextHolder.getContext()
        .getAuthentication().getUserId();
    return orderService.getOwnerId(orderId).equals(currentUserId);
}
```

---

#### 水平越权——操作维度细分

| 操作类型 | 典型攻击路径 | 示例 |
|---------|------------|------|
| **越权读取** | `GET /api/user/info?uid=1001` → 修改 uid 为 1002 | 查看他人个人信息、订单、收货地址 |
| **越权修改** | `POST /api/user/update` Body: `{"uid":1002, "email":"att@x.com"}` | 篡改他人资料 |
| **越权删除** | `DELETE /api/order/delete?orderId=1003` → 删除他人订单 | 订单删除、评论删除 |
| **越权新增** | `POST /api/address/add` → 替换 uid 为他人 | 为他人添加收货地址 |

#### 测试关注点（水平越权——挖掘面）

```
- 个人资料页面 URL 中的用户标识参数（GET/POST/Cookie）
- 订单查看/删除接口中的 orderId 参数
- 收货地址管理接口中的 addressId 参数
- 评论删除接口中的 commentId 或 author 参数
- 数据导出功能的用户范围参数
```

**实战案例：**

```
https://www.szalbb.com/user/profile/address
```

### 2.2 垂直越权（Vertical Privilege Escalation）

**定义：** 低权限用户执行高权限用户专属的操作。服务端仅校验了"是否登录"而未校验"角色/权限级别是否匹配"。

**Pikachu 靶场代码分析：**

```php
// op2_admin_edit.php —— 管理员添加用户页面
if (!isset($_SESSION['username'])) {
    // 仅校验是否登录
    header("Location: login.php");
    exit;
}
// 未校验登录用户的 role/level 是否为管理员
// 任何已登录用户均可执行添加用户操作
$sql = "INSERT INTO users (username, password, level) VALUES (?, ?, ?)";
```

> **关键缺陷：** 代码仅通过 `isset($_SESSION['username'])` 判断认证状态，**未区分用户角色级别**。普通用户 pikachu (level=2) 抓取管理员 admin (level=1) 的添加用户请求后，替换 Cookie 为自身凭证，即可成功创建新用户。

**测试入口 → 篡改点 → 预期危害：**

```
① 测试入口：登录管理员 admin → 执行添加用户操作 → 截获完整请求（URL + Body）
② 篡改点：  登录普通用户 pikachu → 将管理员请求中的 Cookie 替换为普通用户 Cookie → 重放
③ 预期危害： 普通用户越权添加管理员账户，实现持久化权限维持
```

**参考文章：**

```
https://www.cnblogs.com/dummersoul/p/13475010.html
https://mp.weixin.qq.com/s/NWQzocejukT1RytttpP1ew
```

**修复建议：**

```java
// Spring Security 角色注解
@Secured("ROLE_ADMIN")  // 仅 ADMIN 角色可访问
@PostMapping("/admin/user/add")
public Result addUser(@RequestBody UserDTO user) {
    return userService.createUser(user);
}

// 或自定义拦截器
@Component
public class AdminInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) {
        User user = (User) request.getSession().getAttribute("user");
        if (user == null || user.getRole() != Role.ADMIN) {
            response.sendError(403, "权限不足");
            return false;
        }
        return true;
    }
}
```

### 2.3 接口未授权访问（Unauthenticated API Access）

**漏洞根因：** 服务端 API 接口未做身份认证校验，攻击者在未登录或无有效 Token 的情况下可直接访问本应受保护的接口并获取敏感数据。

**测试方法：**

```
① 登录账户 A → 访问个人信息接口 → 记录完整 URL 及请求参数
② 清除浏览器 Cookie 或在 Repeater 中删除 Cookie/Authorization Header → 重新发送请求
③ 若仍返回正常数据（非 401/403），则存在未授权访问漏洞
```

**高效检测策略：** 在 Burp Target → Site Map 中按 MIME Type 筛选 `json`、`script`、`xml` 类型的响应，将疑似数据接口的 URL 在无认证状态下直接访问验证。

**修复建议：**

```java
// 统一认证拦截器
@Component
public class AuthInterceptor implements HandlerInterceptor {
    // 白名单路径
    private static final List<String> WHITE_LIST = Arrays.asList(
        "/api/login", "/api/register", "/api/public/**"
    );

    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) {
        String path = request.getRequestURI();
        if (WHITE_LIST.stream().anyMatch(path::matches)) {
            return true;
        }
        String token = request.getHeader("Authorization");
        if (token == null || !tokenService.validate(token)) {
            response.sendError(401, "未授权访问");
            return false;
        }
        return true;
    }
}
```

## 第3章：业务数据篡改

> **核心原理：** 服务端信任客户端提交的数据参数，未在服务端进行独立的二次校验或未从可信数据源（数据库/Session）重新获取关键业务数值，导致攻击者可篡改金额、数量、折扣等参数。

### 3.1 支付金额篡改

**漏洞根因：** 订单金额从客户端提交的参数中直接读取（如 `total=1`），服务端未从数据库中重新查询商品实际价格进行比对。

**测试入口 → 篡改点 → 预期危害：**

```
① 测试入口：电商下单页面 → 选择商品 → 进入支付确认页面
② 篡改点：  拦截支付请求 → 将 total/price/amount 参数修改为 0.01 或负数
③ 预期危害： 以极低或零成本完成支付，实现商品非法获取
```

**实战案例：**

```
https://cciccbook.jianshe99.com/order/toOrderPage?total=1&orderId=106
```

**修复建议：**

```java
// 服务端重算订单金额
@PostMapping("/order/pay")
public Result pay(@RequestBody PayRequest request) {
    // 关键：从数据库重新计算实际金额，不信任客户端传入的 total
    Order order = orderService.findById(request.getOrderId());
    BigDecimal serverTotal = order.getItems().stream()
        .map(item -> item.getPrice().multiply(BigDecimal.valueOf(item.getQuantity())))
        .reduce(BigDecimal.ZERO, BigDecimal::add);

    // 比较服务端计算结果与客户端提交金额
    if (serverTotal.compareTo(request.getClientTotal()) != 0) {
        throw new BizException("订单金额不匹配");
    }

    return paymentService.process(order, serverTotal);
}
```

### 3.2 商品数量/参数篡改

**漏洞根因：** 购物车等接口未对数量参数做合法性校验，允许负值、零值或超大幅值，导致总金额异常或库存溢出。

**测试入口 → 篡改点 → 预期危害：**

```
① 测试入口：加入购物车 → 点击"加入购物车"按钮
② 篡改点：  拦截 POST 请求 → 将 num/quantity 参数修改为 -1 或 9999
③ 预期危害： 商品总价变为负数（倒赚钱）/ 突破限购数量囤货
```

### 3.3 最大限制突破

**漏洞根因：** 服务端对限购/限量等业务规则的校验**仅依赖前端 JavaScript 禁用按钮或输入框 max 属性**，后端接口未做对应的阈值校验。

**修复建议：**

```python
# Django 示例：服务端数量校验
def add_to_cart(request):
    quantity = int(request.POST.get('quantity', 1))
    product = Product.objects.get(id=request.POST.get('product_id'))

    # 服务端校验最大购买数量
    if product.max_per_user and quantity > product.max_per_user:
        return JsonResponse({'error': '超出限购数量'}, status=400)
    if quantity <= 0:
        return JsonResponse({'error': '数量必须���于0'}, status=400)

    cart.add(product, quantity)
    return JsonResponse({'status': 'ok'})
```

### 3.4 优惠券/积分并发滥用

**漏洞根因：** 优惠券、积分等有使用次数限制的权益，在服务端"校验可用次数 → 执行扣减"之间存在非原子操作的时间窗口，并发请求可突破次数限制。

**实战案例：**

```
http://wy.zone.ci/bug_detail.php?wybug_id=wooyun-2016-0196221
```

**修复建议：**

```sql
-- 使用数据库行锁 + 原子更新确保幂等性
UPDATE coupon
SET used_count = used_count + 1
WHERE id = ? AND used_count < max_use
  AND user_id = ?;

-- 若 affected_rows == 0，说明已超出使用次数，拒绝操作
```

## 第4章：业务流程逻辑缺陷

> **核心原理：** 业务是由多个步骤串联的有限状态机（FSM）。当服务端未强制执行步骤间的依赖校验，而是依赖客户端按顺序"合规"访问时，攻击者可通过跳过中间步骤或篡改状态标识绕过业务约束。

### 4.1 步骤跳跃与状态机绕过

**漏洞根因：** 服务端将业务流程的状态校验结果返回给客户端，由客户端"自觉"执行下一步。攻击者可直接访问后续步骤的接口，绕过前置验证。

**案例 1——注册流程绕过：**

```
正常流程：输入手机号 → 发送验证码 → 输入验证码 → 调用注册接口 → 注册成功
攻击流程：直接调用 /api/register 接口，传入任意手机号（跳过验证码环节）
```

```
实战案例：http://www.eyomart.com/Users/index/doregist
```

**案例 2——密码修改流程跳跃：**

```
正常流程：输入用户名 → 发送验证码 → 输入验证码 → 设置新密码 → 修改成功
攻击流程：完成步骤 1、2 后，将步骤 4（/user/setNewPassword）的 URL
          复制到新浏览器窗口直接访问，绕过步骤 3 的验证码验证
```

> **面试高频考点：** 状态机绕过与 CSRF 的核心区别——前者是利用服务端状态校验缺失的垂直逻辑问题，后者是利用浏览器自动携带 Cookie 的横向攻击。

**修复建议：**

```java
// 服务端维护业务流程状态，拒绝跳跃式访问
public class PasswordResetFlow {
    public enum Step { INIT, CODE_VERIFIED, PASSWORD_SET, COMPLETED }

    public void verifyCode(HttpSession session, String code) {
        // ...验证码校验...
        session.setAttribute("reset_step", Step.CODE_VERIFIED);
    }

    public void setNewPassword(HttpSession session, String newPassword) {
        // 关键：强制校验前置步骤是否已完成
        Step currentStep = (Step) session.getAttribute("reset_step");
        if (currentStep != Step.CODE_VERIFIED) {
            throw new BizException("请先完成验证码验证");
        }
        // 执行密码重置...
        session.setAttribute("reset_step", Step.COMPLETED);
    }
}
```

### 4.2 重放攻击（Replay Attack）

**漏洞根因：** 服务端未对关键操作（发送验证码、提交订单、发表评论）的请求做幂等性校验或无重复提交防护，同一请求被重放多次均可产生独立的有效业务结果。

**影响面：**

| 业务场景 | 危害 |
|---------|------|
| 短信接口重放 | 短信轰炸（资损 + 用户体验影响） |
| 邮件接口重放 | 邮箱轰炸 |
| 注册接口重放 | 批量注册垃圾账户 |
| 评论/点赞重放 | 数据污染、刷量作弊 |

**实战案例（短信轰炸）：**

```
http://114.116.219.117/login.html
http://www.canyin.com/sign/register
https://m.gousteel.com/signup
```

> 参考漏洞报告：短信轰炸漏洞

#### 测试关注点（重放与乱序）

```
- 发送验证码接口 → Repeater 重放 → 确认是否产生多条短信
- 提交订单接口 → 重放 → 确认是否重复生成订单
- 评论/点赞接口 → 重放 → 确认是否突破单次限制
- 修改密码步骤跳跃测试 → 直接访问后续步骤接口
- 注册流程中跳过验证码直接调用注册接口
```

### 4.3 并发条件竞争（Race Condition）

**漏洞根因：** 见 1.3 节（认证绕过中的并发部分）。除此之外，业务场景中的并发同样危害严重：

```
实战案例——点赞并发：
https://www.wuweishi.com/food/6024.html
```

**测试入口 → 篡改点 → 预期危害：**

```
① 测试入口：点赞按钮 → 点击一次点赞
② 篡改点：  Burp Intruder → 20 线程并发发送点赞请求
③ 预期危害： 一次点击产生多次点赞计数，操控热度排名
```

**通用修复方案（接口幂等性）：**

```java
// 基于请求唯一键的幂等性设计
@PostMapping("/api/like")
public Result like(@RequestHeader("Idempotent-Key") String idemKey,
                   @RequestBody LikeRequest request) {
    // Redis SETNX 保证同一 idemKey 仅执行一次
    String cacheKey = "idempotent:like:" + idemKey;
    if (!redis.setnx(cacheKey, "1", 3600)) {
        return Result.duplicate("请勿重复操作");  // 幂等返回
    }
    // 执行点赞逻辑...
}
```

## 第5章：密码重置逻辑缺陷

> **面试高频考点：** 密码重置流程是逻辑漏洞的重灾区——涉及验证码校验、Token 管理、身份绑定多个环节，任一环节的缺陷都可能通向任意用户密码重置。

### 5.1 响应包篡改绕过（Response Manipulation Bypass）

**漏洞根因：** 服务端将验证码校验结果（success/false、code 值）返回给客户端，由客户端 JavaScript 根据返回值决定跳转逻辑。攻击者通过中间人劫持篡改响应体，将 "false" 改为 "true" 即可绕过验证码校验。

**测试入口 → 篡改点 → 预期危害：**

```
① 测试入口：密码找回 → 输入目标账号 → 填写任意 6 位验证码
② 篡改点：  拦截服务端响应 → 将 {"code":"false"} 或 {"status":"error"}
            修改为 {"code":"true"} 或 {"code":200,"status":"success"} → 放行
③ 预期危害： 任意验证码均被判定为有效，进入设置新密码页面
```

**实战案例：**

```
https://nlopen.newlink.com/
```

**修复建议：**

```java
// 关键原则：服务端不向客户端返回校验结果的具体值
// 而是通过服务端 Session 状态控制后续步骤的访问权限

// 验证码校验接口——仅返回通用提示
@PostMapping("/reset/verify-code")
public Result verifyCode(@RequestBody CodeRequest req, HttpSession session) {
    String cachedCode = (String) session.getAttribute("reset_code");
    if (!cachedCode.equals(req.getCode())) {
        return Result.error("验证失败");  // 不透露是哪个字段不对
    }
    session.setAttribute("reset_code_verified", true);  // 服务端记录状态
    return Result.ok();
}

// 设置新密码接口——依赖服务端状态而非客户端传入的标识
@PostMapping("/reset/set-password")
public Result setPassword(@RequestBody PasswordRequest req, HttpSession session) {
    if (!Boolean.TRUE.equals(session.getAttribute("reset_code_verified"))) {
        return Result.error("请先完成验证");
    }
    // 执行密码重置...
    session.removeAttribute("reset_code_verified");
    return Result.ok();
}
```

### 5.2 Token 未绑定用户身份

**漏洞根因：** 密码重置 Token 为全局有效凭证，服务端在校验时仅验证 Token 是否存在且有效，未校验该 Token 归属于哪个用户。攻击者获取自己账户的重置 Token 后，修改请求中的用户标识（UID/username）即可重置他人密码。

**实战案例——北京 XXXX 教育科技有限公司任意用户密码重置：**

```
https://www.sanjiatv.com/mall/index.htm
密码找回流程中，输入任意六位数验证码均可跳转至设置新密码页面，修改成功。
```

**修复建议：**

```java
// Token 与用户身份强绑定
String resetToken = UUID.randomUUID().toString();
// 存储结构：reset_token:{token} → uid
redis.setex("reset_token:" + resetToken, 1800, String.valueOf(userId));

// 校验时同时验证 Token 与 UID 的对应关系
String boundUid = redis.get("reset_token:" + inputToken);
if (boundUid == null || !boundUid.equals(request.getUid())) {
    throw new AuthException("重置凭证无效或已过期");
}
```

### 5.3 Token 未失效（Token Reuse）

**漏洞根因：** 密码重置 Token 使用后未即时标记为失效或删除，攻击者可重复使用同一 Token 多次重置密码，或修改 URL 中的 UID 参数配合复用。

**实战案例：**

```
某网站邮箱找回密码链接示例：
http://www.xxx.com/GetPwd?q=0x0531387a5a6c1227e4d6ba0ce16dc72e&uid=3244166

攻击者修改 uid 参数为其他用户 ID，由于 Token(q) 未绑定用户且未失效，
可直接重置任意用户密码。
```

**修复建议：**

```java
// Token 一次性使用
String tokenValue = redis.get("reset_token:" + token);
if (tokenValue == null) {
    throw new AuthException("Token 已使用或已过期");
}
// 先删除再执行业务，防止并发复用
redis.del("reset_token:" + token);
// 执行密码重置...
```

### 5.4 绑定手机/邮箱越权

**漏洞根因：** 用户绑定手机号或邮箱的接口存在越权缺陷，攻击者可越权将其他用户的手机号/邮箱绑定至自己账户，随后通过"忘记密码"的正常流程即可重置他人密码。

**攻击链：**

```
① 越权绑定受害者手机号至攻击者账户
② 使用"忘记密码"→"手机验证"正常流程
③ 收到本属于受害者的验证码 → 完成密码重置
```

```
- 验证码响应体回显测试（检查 Response Body）
- 验证码暴力破解测试（4 位纯数字无次数限制）
- 接口参数账号篡改测试（修改 phone/uid 参数）
- 响应状态值篡改测试（修改 code/success/status 字段）
- Token 未绑定测试（A 的 Token 重置 B 的密码）
- Token 复用测试（同一 Token 多次重置）
- 邮箱重置链接参数遍历测试（修改 uid 或 token 中的用户标识段）
```

## 附录：通用防御原则

> 以下原则适用于上述所有漏洞类别，是逻辑漏洞防御的基石。

1. **永远不信任客户端输入：** 所有关键业务参数（金额、数量、用户标识、角色）必须从服务端可信数据源（Session/数据库）重新获取，**绝不**直接使用客户端传入值。
2. **服务端状态强制流转：** 多步骤业务流程的状态管理必须在服务端 Session 中进行，禁止依赖客户端状态或响应体返回值控制流程分支。
3. **接口幂等性设计：** 所有产生副作用的操作（支付、扣券、点赞、发短信）必须通过唯一请求键（Idempotent-Key）+ Redis SETNX 或数据库行锁实现幂等。
4. **凭证与主体强绑定：** 验证码、重置 Token 等临时凭证必须与用户身份绑定存储，校验时同时验证"凭证有效性"与"用户身份一致性"。
5. **基于 Session 的统一权限拦截：** 构建中间件/拦截器对所有受保护接口进行统一的认证校验与角色权限判定，避免在每个 Controller 中分散实现，降低遗漏风险。
6. **敏感操作速率限制：** 短信发送、登录尝试、验证码校验等接口必须设置基于 IP + 用户维度的频率限制。
